MiniRank — Process Document

How MiniRank was built with an agent across eighteen sessions: the plan, the prompts that mattered, the full session log, and what I'd do differently.

1. Plan

MiniRank tracks keyword rankings for one configured website: PHP 8 + SQLite, plain server-rendered HTML, CSS and vanilla JS, no framework, no package manager, no extra dependencies. Every milestone was planned in advance with the agent and verified against acceptance checks before being marked complete.

Key decisions

Routing: split entry/action pattern

  • GET entry files (public pages): public/index.php (list + search), public/keyword.php (detail, ?id=).
  • POST action files (state-changing, under public/actions/): keyword-create.php, keyword-update.php, keyword-delete.php → post-redirect-get back to the list; refresh.php → returns JSON for the AJAX update (M3).
  • Every action file refuses non-POST and verifies CSRF before touching state.
  • No front controller, no router.php. php -S localhost:8000 -t public serves everything directly.

Database guarantees (positions)

  • UNIQUE(keyword_id, recorded_on) → one position per keyword per day (refresh upserts today's row).
  • FOREIGN KEY (keyword_id) REFERENCES keywords(id) ON DELETE CASCADE → deleting a keyword removes its whole history.
  • PRAGMA foreign_keys = ON set per connection in src/db.php (SQLite default is off — easy to miss).
  • CHECK (position BETWEEN 1 AND 100) → domain bound enforced in schema.
  • History = dated rows in positions; the UNIQUE(keyword_id, recorded_on) constraint doubles as the index for history/trend lookups.
  • CREATE TABLE IF NOT EXISTS + idempotent init.

Initial proposed structure (superseded)

public/index.php, public/keyword.php # GET entries public/actions/{keyword-create,keyword-update,keyword-delete,refresh}.php # POST public/assets/{app.css,app.js} lib/{db,csrf,repo,trend}.php views/{layout,list,detail}.php seed.php, data/.gitkeep, .gitignore, README.md, AGENTS.md, process/notes.md

This first cut proposed lib/, views/, and public/assets/, but the build settled into a simpler layout — see the actual structure below.

Milestones (per the candidate brief) and how each was delivered

# Brief definition Delivered as
M1 Keywords CRUD: add/edit/delete the keywords (search phrases) tracked for one configured website. Single-user app — no login. Three sub-slices: keyword creation (form + CSRF + 303-PRG), then edit/delete with safe 404s and cascade delete.
M2 Seeded history: a seed script creates demo keywords with ~30 days of daily positions (1–100). bin/seed.php + transactional minirank_seed() (6 keywords × 30 consecutive days, idempotent), plus the seven-day trend logic.
M3 Refresh simulation: a "Refresh positions" button generates today's positions server-side and updates the page via AJAX, without a full page reload. POST JSON endpoint (public/actions/refresh.php) with a same-day UPSERT, vanilla JS updating cells in place, real-browser no-reload verification.
M4 Keyword list: every keyword with its current position, a 7-day trend indicator (improved / declined / stable), and a text search. public/index.php list + search with escaped output and LIKE-escaped queries.
M5 Keyword detail: a page per keyword showing the position history as a table. public/keyword.php with newest-first history table, empty state, safe 404s.
M6 Security basics: parameterized queries (no SQL built by string concatenation), escaped output, and no secrets committed to the repository. Enforced in every slice from the start (prepared statements only, htmlspecialchars everywhere, POST-only + CSRF); confirmed end-to-end by the final security audit.
M7 Runs in 5 minutes: README with setup steps, a seed command, and a one-command start (php -S ... or docker compose up). Database: SQLite (recommended) or MySQL. README with requirements, config, seed, one-command php -S start, and test instructions (SQLite).
M8 Responsive: usable at phone width. Functional beats beautiful — we are not grading pixel-perfection. CSS-only responsive pass, verified in headless Chrome at 375×812 with no page-level horizontal overflow.

Build order differed from the milestone numbers: scaffold → database foundation → M2 (seed/trend) → M4 (list/search) → M5 (detail) → M1 (create, then edit/delete) → M3 (refresh) → M8 (responsive) → final audit + M7 (README). M6 was built into every slice rather than as a separate stage.

Slice discipline

  • Slice 1 — scaffolding: .gitignore, data/.gitkeep, AGENTS.md written up front from already-made decisions, so the conventions shaped every later slice. Git/file-level verification only, no PHP yet.
  • Every slice was planned with the agent first (files, behavior, acceptance checks, verification commands), reviewed before implementation, then verified against all existing suites plus its own new tests before AGENTS.md was updated and the commit was made.
  • Each milestone shipped with dedicated unit tests, HTTP smoke tests against the PHP built-in server, and CSRF/post-only/safe-404 coverage.

What I would change in hindsight

  • Keep the same architecture — the split entry/action pattern and the per-connection PRAGMA foreign_keys + constraint-backed schema were the right calls and held up across all eight milestones.
  • Decide less too early. Some conventions were locked before there was code to justify them; several were only proven (or needed adjusting) once the first slices ran.
  • Create the reusable test setup earlier. A shared helper for scratch DBs, seeding, and the HTTP smoke harness would have saved repeated setup code across tests/.
  • Record evidence as I go. I treated verification output as ephemeral instead of capturing it next to each slice — see the Retrospective.

2. Prompts & fixes

Three real prompts that shaped the build — including one that failed and was caught only by re-running the tests myself — followed by the full session log.

Failed — caught by re-running tests

Prompt 1 · Deterministic seed data and seven-day trend logic

<role> you are a brilliant senior PHP backend engineer responsible for a billion dollar company data layer. Follow the project conventions in AGENTS.md and verify assumptions against PHP 8.0 and SQLite.</role>

plan the next slice: deterministic seed data and seven day trend logic. the seed must create six demo keywords with 30 consecutive daily positions, completely safe when run repeatedly — do not create duplicate keywords or dates. As per AGENTS.md trend uses current position and newest position on or before seven days. LOWER IS BETTER. Cover improved, declined, stable and missing history cases. Include reusable tests, files that will be affected, acceptance checks, exclusions. DONT EDIT FILES OR USE GIT

What the AI got wrong: The agent reported the tests successful and clean. When I ran the run commands myself, php tests/seed_trend_test.php reported 34 passed, 1 failed, plus an unlink warning. The agent's summary asserted success it hadn't actually achieved, and the unlink warning meant a temp file cleanup path was wrong — a signal that files could be left behind.
How I caught it: I never trust a "tests pass" summary — I ran the exact test command from the agent's own verification list and compared the output. The mismatch (34/1 + warning) was the discrepancy that forced the fix.
The fix (follow-up prompt): "for the seed_trend_test.php 34 passed but one failed with an unlink warning. diagnose and fix. make sure atomicity tests cause failures on a fresh database so we can diagnose. make sure no raw exception details are exposed. run every lint SEPARATELY then both complete test suites. update AGENTS.md after everything passes with no warnings or leftover files. stay within this slice. DO NOT USE GIT."
The agent then fixed the failing check and the unlink warning, made the atomicity tests fail loudly on a fresh DB, ran each lint separately, ran both suites to green with no warnings or leftover temp files, and updated AGENTS.md.
Corrected by spec review

Prompt 2 · M1 — Keyword edit and delete

<role> You are the best senior PHP engineer continuing MiniRank. read AGENTS.md, inspect the existing keyword, session, detail and code. you are well indulged in the cybersecurity field and your code is known to be impenetrable, safe, secure and concise.</role>

plan this bounded slice to complete M1 | adding keyword edit and delete. must reuse all the existing ID parsing, phrase validation, CSRF, flash and database helpers. add escaped edit form and separate POST actions for update and delete. update must work with the existing rules and case insensitive cases, also allowing keyword to keep current phrase. delete means SQLite removes all related position history. handle invalid/missing/array/unknown/deleted IDs safely. Wrong methods return 405. missing and incorrect CSRF return 403 with no data changing. successful actions use 303 post/redirect/get. add specific tests, HTTP checks, and run every suite. deletion leaves no positions, deleted keyword RETURNS 404. stay within the scope M1 ONLY. use simplest PHP 8.0 design. list proposed files, acceptance checks, verification commands. DO NOT EDIT FILES OR USE GIT.

What the AI got wrong: The agent's plan routed invalid/missing/id[]/unknown/deleted IDs to an "Keyword not found." error flash followed by a 303 redirect to ../index.php — the wrong status for that case. 303 is reserved for successful changes and ordinary validation/duplicate failures; a not-found/malformed ID must be a safe 404 on the edit page and both POST actions, with no mutation.
How I caught it: I read the agent's reported behavior against the safe-404 convention in AGENTS.md and the M1 brief ("deleted keyword RETURNS 404"). Error-flash-then-redirect contradicted both, and it would have made delete/edit smoke tests assert the wrong status.
The fix (follow-up prompt): "correct the following: Invalid/missing/id[]/unknown/deleted id → error flash 'Keyword not found' → 303. return safe 404 from edit page and both POST actions, no mutation; 303 is for only successful changes and ordinary validation/duplicate failures. // MAKE SURE using tests that ONLY the deleted keyword's history disappears, other keywords remain, and global orphan count is 0. KEEP EVERYTHING ELSE UNCHANGED. DO NOT EDIT FILES OR USE GIT."
The edit page and both POST endpoints then returned safe 404s for invalid/missing/array/unknown/deleted IDs with zero mutation, and the smoke tests asserted that deleting one keyword leaves other keywords and their seeded history untouched, with a global orphan-position count of 0.
Bounded, correct on first pass

Prompt 3 · M3 — Refresh positions with AJAX (no reload)

<role> you are the best PHP engineer in a trillion dollar company. continue MiniRank: read AGENTS.md and inspect the current application and tests before proposing anything. You are extremely knowledgeable in the domain of security and AJAX, and handle each and every single edge case perfectly.</role>

PLAN the smallest complete M3 slice. add a refresh positions control that generates today's simulated positions server-side for all keywords and updates visible current positions and trend with vanilla JS without navigating or fully reloading the page. follow all database and security rules in AGENTS.md; handle keyword with no history, repeated refreshes, transaction failure, CSRF, wrong methods, safe JSON errors, browser request failure. include concise reusable tests, all existing verification suites, real-browser verification of the no-reload behavior; leave runtime data out of tests. list the suggested files, behaviors, acceptance checks, verification steps. stay within the slice. DO NOT EDIT FILES, DO NOT USE GIT.

Why this one mattered: The prompt pushed the whole slice to a pure planning stage (no edits, no git), which forced a complete acceptance checklist up front. The agent returned a tight design: a transactional same-day UPSERT (INSERT ... ON CONFLICT (keyword_id, recorded_on) DO UPDATE) in src/refresh.php, a POST-only JSON endpoint with 405/403/500 handling and JSON_HEX_*/JSON_INVALID_UTF8_SUBSTITUTE encoding, and vanilla JS (public/js/refresh.js) that updates table cells via textContent only on full success and never mutates the DOM on failure. The real-browser no-reload check was listed as a manual step and later confirmed in Chrome headless at phone width.

3. Retrospective

What I would do differently

  • Have the agent summarize each slice immediately after finishing it — with the prompt(s) attached, plus every mistake, its fix, and the outcome — instead of reconstructing the record at the end. That lesson is what produced the session log in section 2.
  • Record evidence as I go: keep the lint/test outputs and HTTP smoke results alongside each slice's notes so nothing has to be re-run (or guessed) later.
  • Never accept a "tests pass" claim on trust — the seed/trend failure (34 passed, 1 failed, unlink warning) was only caught by running the exact command myself. Verify the agent's verification.
  • Create the reusable test setup earlier (shared scratch-DB, seeding, and HTTP smoke helpers) to cut repeated boilerplate across tests/.
  • Decide less too early; let the first slices prove the conventions before locking them into AGENTS.md.
  • Do the same architecture again: split GET entries from POST actions, per-connection PRAGMA foreign_keys, constraint-backed schema, CSRF on every mutation, and 303-PRG for success while reserving safe 404s for missing/unknown records.

Time spent

Roughly 7 hours of focused work across the build: planning and scaffolding (architecture decision + AGENTS.md conventions), database foundation, M2 (seed/trend), M4 (list/search), M5 (detail), M1 (create, then edit/delete), M3 (refresh with real-browser no-reload verification), M8 (responsive), and the final audit + M7 (README) — including the unbudgeted rework from the seed/trend test failure and the edit/delete 404 correction.

Estimate only — I did not time-box the sessions, and the edit/delete 404 correction plus the seed/trend test failure both consumed unbudgeted time that a "summarize each slice" habit would have surfaced sooner.
